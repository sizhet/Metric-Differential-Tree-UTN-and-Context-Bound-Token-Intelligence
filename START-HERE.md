
# 2. The Core Idea

Consider the word:

```text
rollback
```

Its meaning may depend on context:

```text
rollback@DatabaseTransaction

rollback@Deployment

rollback@GitRepository
```

The lexical token remains the same.

The structural context changes.

This repository proposes that the context should not remain implicit whenever it is important.

Instead:

```text
token
+
explicit structural context
```

can be represented as:

```text
token@context
```

This is called:

> **Context-Bound Token — CBT**

---

# 3. Why MDT Comes Before CBT

CBT needs a trustworthy context identity.

MDT-UTN provides the structural process that produces it.

> **MDT-UTN is the context-identity producer.
> CBT is the context-identity carrier.**

# 5. Typing First, Naming Second

UTN is split into two layers.

## Universal Typing

Ask:

```text
Can these structural individuals
legitimately share a parent type?
```

Use:

```text
metric similarity
positive evidence
counter-evidence
policy
historical cases
validation
```

Possible outcomes:

```text
merge
reuse existing type
create new type
split
leftover
defer
```

---

## Universal Naming

Only after structural typing is justified do we ask:

```text
What should this type be called?
```

Therefore:

> **Typing does not have to wait for Naming.**

---

# 6. The Leaf Principle

Leaves preserve structural individuals.

A leaf should retain:

```text
original context
original name
source
version
provenance
evidence
```

The rule is:

> **Fold upward; do not erase downward.**

Parent types summarize structural commonality.

Leaves preserve original evidence.

---

# 7. Similarity Is Not Truth

Metric similarity identifies candidates.

It does not authorize merging by itself.

Therefore every important UTN merge should include:

```text
Search FOR the merge
+
Search AGAINST the merge
```

This is:

> **Two-Way Structural Search**

The second direction looks for:

```text
counter-examples
behavioral differences
version conflicts
policy conflicts
semantic conflicts
exceptions
```

---

# 8. Leftover Is a Valid Result

A structural system should not force every target into an existing type.

Valid outcomes include:

```text
UNKNOWN

AMBIGUOUS

LEFTOVER
```

A leftover may later become:

```text
Repeated Similar Cases
        ↓
Metric Cluster
        ↓
New MDT Branch
        ↓
New UTN Type
```

Thus unresolved structure can become future intelligence.

---

# 9. Local First, Universal Through Composition

A universal UTN does not need to begin as one global tree.

Instead:

```text
Local UTN
   ↓
Subsystem UTN
   ↓
Repository UTN
   ↓
Organization UTN
   ↓
Domain UTN
   ↓
Evolving Universal UTN
```

The core principle is:

> **Fold locally, merge folded structures globally, and unfold only where ambiguity requires deeper inspection.**

# 16. The MDT-UTN Algorithm in One Page

The core algorithm is:

```text
STEP 1
Preserve the original target context.

STEP 2
Encode context as GenericContainerStarmap.

STEP 3
Calculate Metric Similarity / Distance.

STEP 4
Localize the target in the MDT.

STEP 5
Form local typing candidates.

STEP 6
Search positive structural evidence.

STEP 7
Search counter-evidence.

STEP 8
Separate explicit leftovers.

STEP 9
Apply Metric / UTN Policy.

STEP 10
Reuse or create structural type.

STEP 11
Assign canonical name / aliases if needed.

STEP 12
Validate.

STEP 13
Commit with provenance and version.

STEP 14
Fold the successful or failed decision
into future structural experience.
```

# 20. CBT Is a Logical Unit, Not Necessarily One Tokenizer Token

The notation:

```text
token@context
```

does not imply that an existing tokenizer will encode it as one atomic vocabulary token.

It may be split internally.

For v1.0.0, CBT should be understood as:

> **a lexical-symbolic structural encoding unit**

that can be introduced without changing model architecture.

Tokenizer-level integration is a possible later implementation direction.
