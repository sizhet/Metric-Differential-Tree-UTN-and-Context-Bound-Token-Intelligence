# Key Idea

The repository begins with a simple but important reversal:

> **Context is primary; naming is secondary.**

Traditional naming often begins from symbols and attempts to infer identity.

MDT-UTN instead follows:

```text
Target
   ↓
Structural Context
   ↓
Metric Position
   ↓
Structural Neighborhood
   ↓
Structural Type
   ↓
Name
```

This leads to the central thesis:

> **UTN is not fundamentally a naming problem. It is a context-preserving structural localization, folding, typing, and controlled naming problem over a Metric-Differential Tree.**

---

# Major Contribution 1 — Metric-Differential-Tree UTN

A target context is represented through a **GenericContainerStarmap** and compared using policy-governed Metric Similarity / Distance.

The resulting structure is organized into a **Metric-Differential Tree (MDT)**.

```text
Context
   ↓
GenericContainerStarmap
   ↓
Metric Similarity / Distance
   ↓
MDT
   ↓
Structural Neighborhood
   ↓
Per-Node UTN Intelligence
```

This converts a global typing problem into localized structural decisions.

Canonical rule:

> **Localize first; compare locally.**

---

# Major Contribution 2 — Typing First, Naming Second

MDT-UTN explicitly separates:

```text
Universal Typing
```

from:

```text
Universal Naming
```

Typing asks:

> Can these structural individuals legitimately share a type?

Naming asks:

> What symbolic name should represent that validated type?

Therefore:

> **UTN is Typing-first, Naming-second.**

A Structural Type may exist before a final human-readable name exists.

---

# Major Contribution 3 — Per-Node UTN Intelligence

The local UTN algorithm operates primarily around MDT leaves and their direct structural neighborhood.

Canonical sequence:

```text
Context Preservation
      ↓
Metric Candidate Formation
      ↓
Positive Evidence
      ↓
Two-Way Counter-Evidence
      ↓
Leftover Separation
      ↓
Policy Evaluation
      ↓
Structural Type Formation
      ↓
Naming
      ↓
QA / Validation
      ↓
Commit
      ↓
Learn
```

The MDT supplies localization.

Per-Node Intelligence supplies the structural decision.

---

# Major Contribution 4 — Leaf Preservation and Explicit Leftover

The framework establishes the **Leaf Immutability Principle**:

> **Fold upward; do not erase downward.**

Leaves preserve original structural evidence such as:

```text
context
name
source
version
provenance
evidence
```

The framework also treats **Leftover** as an explicit structural state.

A case that does not fit existing types should not be forcibly classified.

```text
Unknown
   ↓
Leftover
   ↓
Repeated Evidence
   ↓
New Structural Branch
   ↓
New Type
```

---

# Major Contribution 5 — Two-Way Structural Search

Metric similarity is treated as a candidate generator rather than final truth.

Instead of:

```text
Similarity
→ Merge
```

MDT-UTN uses:

```text
Similarity
   ↓
Candidate
   │
   ├── Positive Evidence
   │
   └── Counter-Evidence
            ↓
       Decision
```

Canonical rule:

> **Similarity creates candidates, not truth.**

Counter-evidence is a first-class part of structural intelligence.

---

# Major Contribution 6 — Composable UTN

Universal structure does not need to be created through one global operation.

Instead:

```text
Local
   ↓
Subsystem
   ↓
Repository
   ↓
Organization
   ↓
Domain
   ↓
Evolving Universal UTN
```

The key tree-merge principle is:

> **Fold locally; merge folded structures globally; unfold only where ambiguity requires deeper inspection.**

This allows local UTN structures to become progressively composable while preserving provenance and local identity.

---

# Major Contribution 7 — Context-Bound Token

The release introduces the **Context-Bound Token (CBT)**.

Canonical notation:

```text
token@context
```

Examples:

```text
open@FileIO

open@NetworkSocket

commit@GitRepository

rollback@DatabaseTransaction
```

CBT exposes explicit structural identity in a form that existing token-oriented systems can consume.

---

# Dual-Track Encoding

The preferred design preserves both:

```text
raw token
+
Context-Bound Token
```

Example:

```text
open

open@FileIO
```

The raw token preserves:

```text
baseline semantics
broad recall
compatibility
```

The CBT adds:

```text
structural precision
context localization
routing evidence
```

Canonical rule:

> **Keep the token; bind the context.**

# Major Contribution 8 — Baseline-Preserved Context Injection

The release introduces **Baseline-Preserved Context Injection (BPCI)**.

Let:

```text
S0 = baseline input

C = explicit structural context

S1 = context-enhanced input
```

Then:

```text
S1 = S0 + C
```

with the required invariant:

```text
Recover(S1) = S0
```

Therefore every context-enhanced input retains its own recoverable control group.

Canonical principle:

> **Context should augment the baseline, not erase it.**

---

# Context Gain

The effect of structural context can then be measured as:

```text
Context Gain
=
Score(Context-Enhanced)
-
Score(Baseline)
```

Possible outcomes include:

```text
Positive Gain

Neutral Gain

Negative Gain
```

This is important because more explicit context is not assumed to be automatically beneficial.

---

# Major Contribution 9 — Context Density Policy

The release distinguishes:

```text
Which Context?
```

from:

```text
How Much Context?
```

It introduces **Context Injection Density (CID)** as an experimental and policy variable.

Conceptually:

```text
CID
=
Injected Context-Bound Units
/
Relevant Baseline Units
```

The preferred policy starts sparse and increases context only when additional evidence provides measurable value.

> **Select the right context. Inject it sparsely. Add only complementary evidence.**

---

# Context Depth, Density, and Breadth

Three independent dimensions are separated:

```text
Depth
→ How specific?

Density
→ How much?

Breadth
→ How many structural dimensions?
```

This allows Context Policy to control structural evidence more precisely.



Once structural context can be localized, typed, preserved, and addressed, the same structural identity can potentially be reused across many intelligence mechanisms.
